# Android APK 功能调查

> 前置：若尚未产出可读源码工程，先用同仓库的 `android-apk-decompile` 技能（`skills/android-apk-decompile/SKILL.md`）完成反编译；本技能的起点是「已有源码工程 + 一个待查功能」。

目标是回答用户当前业务问题，给出可核查的代码位置、行为条件与未确认项；新版本重新验证，不把旧包、DEBUG 包或缓存资料当作当前事实。

## 工作流程

1. 确定目标 APK、版本、包名、SHA-256，检查现有分析结果与用户指定的输出目录；保留用户文件，删除或覆盖旧产物只在已获授权且范围明确时进行。若用户要求所有文件留在某处，主动将工具输出、解压文件、日志和可配置临时目录放在那里，并说明工具自管临时文件的实际情况。
2. 基于用户线索列出要回答的问题，从类、接口、页面 ID、日志、资源或页面截图定位入口。优先复用同一 APK 的已验证结果；用户指定 REA 时，按当前可用 REA Android 能力先查包、类、方法和静态引用；如不可用，说明限制并用现有 JADX、DEX 或其他可用工具继续，不要声称替代品是 REA。
3. 沿实际调用链向上追到触发源、前置条件，向下追到数据获取、状态变化、页面消费和失败降级。明确线程、异步回调和触发时间；分析请求与 UI 的独立分支，区分“未请求”“拿到数据但未使用”“未展示”三类问题。
4. 同时检查配置与状态：默认值、配置生效时机、账号/设备实验归属证据、系统权限、初始化标记、缓存的键/有效期/读取策略、频控和场景资格。切勿把配置开关等同于 AB 实验；白名单是否真正下发、值是否生效需要设备或可靠配置证据。
5. 涉及 KRN/RN/动态页面时，检查包内文件及嵌套容器、路由参数、编码、入口和加载失败降级；记录搜索范围。找不到 bundle 不等于不存在或一定远程下载；没有页面代码时不推断渲染和交互。注意不同接口可能分别负责图片和文案。
6. 涉及弹窗互斥时，区分业务资格/已展示频控、特定弹窗状态检查、框架队列、生命周期拦截和真实全局互斥。沿实际展示路径检查 `show` 与 `showImmediate`、原生与动态容器、唯一 ID、开关、配置与关闭/丢弃回调；不要仅凭队列类存在就认定业务使用它。截图仅是外观线索，不足以证明实际组件和开关状态。
7. 在给新需求提出方案前，写出当前行为、需求触发场景和期望变化；定位最小改动点及上下游契约，评估开关、兼容/降级、缓存、埋点、生命周期、互斥与回归影响。只在用户要求实施时修改目标项目；分析任务输出方案和验收矩阵即可。需求不明确时先基于现有证据分析，再指出阻塞决策的信息。

## 证据和验证

- 对关键结论给出可点击的本地文件和行号、实际类名/混淆名、APK 身份和证据 ID（如 REA 返回）。静态事实、合理推断和运行时观察分开。动态调用、服务端实验和页面渲染没有观察时标记未知。
- JADX 有控制流警告、空分支、无法编译或逻辑自相矛盾时，核对 REA 方法输出、smali/DEX 指令或 fallback；说明具体可信边界，不能将错误 Java 当真实逻辑。分 DEX 反编译可能缺跨 DEX 类型上下文；全量输出统计错误数和覆盖，不把文件数量当完整性证明。
- 优先给最短的复现/断点路径：输入和实际配置 → 分支判断 → 请求和响应 → 缓存 → 页面参数 → 展示/拦截/降级。设备或抓包仅在用户授权及环境允许时进行；不为了取证清空数据、修改权限或改变线上状态而擅自操作。请求失败、缓存命中、初始化时序和异步竞争要分别检查。
- 交付按用户需要给链路图、条件表、关键代码链接、已证实/未知、诊断步骤和新需求影响；若截图或包内证据不足以确定具体分支，明确说明如何验证。需要详细经验和检查表时阅读 [references/ai-head-image-case.md](references/ai-head-image-case.md)。
